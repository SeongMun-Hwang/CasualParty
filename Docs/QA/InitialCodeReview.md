# CasualParty 초기 코드 검토

검토일: 2026-11-04. 대상: 현재 작업 디렉터리의 코드와 씬·프리팹·애니메이션 파일.

Unity 플레이 모드, Android 빌드 및 실기기 테스트는 수행하지 않았다. 아래의 관찰은 정적 분석 결과이며, 재현 절차는 실행 결과가 아닌 검증 제안이다. 기존 ProjectSettings 변경 사항은 수정하지 않았다.

## 기능과 상태 흐름

빌드 씬은 Title, Blockdoku_2D, 10SUM, MineSweeper, 2048 순서다. SettingsManager, AdManager, UI_Functions는 씬 전환 후 유지된다. 게임 매니저는 게임별로 생성된다.

| 게임 | 시작·진행 | 종료 | 영속 데이터 |
| --- | --- | --- | --- |
| 블록도쿠 | 저장 보드가 있으면 자동 복원. 9×9 배치, 행·열·3×3 제거, 콤보·대칭·전체 제거 보너스 | 남은 블록 모두 배치 불가능 | save.json, blockData.json, personal.json |
| 10SUM | 매 진입 시 새 10×17 보드, 1~9 숫자를 거의 균등하게 섞음. 직사각형 합 10이면 제거 칸 수 득점 | 120초 만료 | TenSum.json의 최고 점수 |
| 지뢰찾기 | 난이도 선택 후 첫 열기에서 지뢰 생성·타이머 시작. 첫 칸 주변 3×3 안전 | 지뢰 선택 또는 안전 칸 전체 공개 | MineSweeper.json의 난이도별 최단 시간 |
| 2048 | 저장 보드 자동 복원 또는 두 타일로 시작. 유효 이동 후 2(90%)·4(10%) 생성 | 빈칸·인접 동일 값이 없을 때. 2048 달성 별도 승리 처리 없음 | 2048.json, PlayerPrefs의 2048_HighScore |

설정은 setting.json에 저장한다. 진동 값은 Handheld.Vibrate 호출 여부를 판별하며 강도나 길이에 전달되지 않는다. 블록도쿠 UIManager_2D.Vibrate는 비어 있다.

## 우선 검증 항목

아래 우선순위는 사용자 영향과 코드 근거에 따른 잠정 순서다. 정식 결함 확정과 심각도 결정은 실행 재현 후 진행한다.

### R01. 2048 합치기 결과보다 저장·종료 판정이 먼저 실행됨 — 높음

- 근거: Tile2048.MergeInto는 0.1초 이동 애니메이션의 OnComplete에서 대상 숫자를 두 배로 만든다. GameManager2048.HandleMove는 Move 반환 직후 SpawnTile, SaveBoard, CanMove를 실행한다.
- 영향: 점수는 합친 결과로 저장되지만 보드는 합치기 전 숫자로 저장될 수 있다. 마지막 수에서 합치기 전 숫자로 이동 가능 여부를 판정할 수도 있다. 다음 유효 이동에서 다시 저장되기 전까지 보드 불일치가 남을 수 있다.
- 검증: 2+2를 합친 후 다른 유효 이동 없이 타이틀로 나가 재진입한다. 타일이 4인지, 점수와 보드가 일치하는지 확인한다. 보드가 가득 차는 마지막 수에서도 확인한다.
- 관련: Assets/Scripts/Games/2048/Tile2048.cs, GameManager2048.cs, GridManager2048.cs.

### R02. 2048 애니메이션 중 추가 입력을 차단하지 않음 — 높음

- 근거: 입력→HandleMove→Move 경로에 이동 중 상태 잠금이 없다. 다음 Move가 mergedThisTurn을 초기화해도 이전 합치기의 숫자 변경은 아직 예약 상태일 수 있다.
- 영향: 빠른 연속 스와이프에서 이전 숫자를 기준으로 이동·합치기가 이어지거나, 이전 애니메이션 콜백이 다음 턴의 타일 상태를 변경할 수 있다.
- 검증: 합치기 직후 0.1초 이내 반대 방향 또는 같은 방향을 입력한다. 느리게 입력한 결과와 타일 총합·점수·합치기 횟수를 비교한다. 연속 입력 후 즉시 씬을 나가는 경우도 확인한다.

### R03. 블록도쿠 전체 제거 조건의 계산 순서 오류 — 높음

- 근거: GridManager_2D.CheckForCompletedLines에서 제거 칸에 ClearLogically를 적용한 뒤 점유 칸을 센다. 이 수를 cellsToClear.Count와 비교한다.
- 코드상 결과: 실제 전체 제거라면 남은 칸은 0이므로 제거 칸 수와 같을 수 없다. 반대로 제거 후 남은 칸 수가 제거 칸 수와 같으면 전체 제거로 잘못 판정된다.
- 검증: (1) 마지막 한 줄만 채워 모두 제거, (2) 9칸을 제거하고 관계없는 9칸은 남기는 보드. FULL CLEAR 표시·보너스·콤보를 각각 확인한다.
- 관련: Assets/Scripts/Games/Blockdoku/GridManager_2D.cs의 CheckForCompletedLines.

### R04. 블록도쿠 다음 블록 생성 전 저장본에서 진행 정지 가능 — 높음

- 근거: BlockPlaced가 사용한 블록을 목록에서 제거한다. PlaceBlock은 즉시 저장한다. 제거 연출이 있으면 BlockPlacedRoutine은 대기한 뒤 새 블록을 생성한다. 이 사이에는 빈 블록 목록이 저장될 수 있다. LoadBlockData_2D는 빈 목록을 복원해도 SpawnBlocks를 호출하지 않는다.
- 검증: 마지막 제공 블록으로 줄을 제거한 직후 타이틀로 이동하고 재진입한다. 보드는 있지만 제공 블록이 없는 상태가 발생하는지 확인한다.
- 변형: save.json만 있고 blockData.json이 없는 경우에도 제공 블록 없이 복원될 수 있다.
- 관련: Assets/Scripts/Games/Blockdoku/BlockSpawner_2D.cs, GridManager_2D.cs, GameManager_2D.cs.

### R05. 드래그 중인 블록이 저장에서 탈락할 가능성 — 중간

- 근거: Block_2D.OnPointerDown은 블록의 부모를 Canvas로 변경한다. SaveBlockData_2D는 현재 부모의 spawnPositions 인덱스를 저장하므로 드래그 중이면 -1이다. 로드 시 -1 인덱스는 건너뛴다.
- 검증: 다른 블록의 제거 연출 중 추가 블록을 잡고, 앞선 배치의 지연 저장이 실행될 때까지 드래그를 유지한다. 이후 시스템 뒤로 가기로 타이틀에 나가 재진입하고 제공 블록 개수를 확인한다. 시스템 뒤로 가기 자체는 저장하지 않으므로 저장 타이밍을 겹치는 것이 핵심이다.
- 관련: Assets/Scripts/Games/Blockdoku/Block_2D.cs, BlockSpawner_2D.cs.

### R06. 모바일 키보드 장치 부재 시 예외 가능 — 높음

- 근거: UI_Functions.Update와 InputManager2048.HandleKeyboardInput이 Keyboard.current를 null 검사 없이 사용한다.
- 검증: 외부 키보드 없는 Android 기기에서 타이틀·2048의 로그와 스와이프 응답을 확인한다. 키보드가 연결된 에디터만으로 판단하지 않는다.

### R07. 지뢰찾기 종료 이후 주변 열기 반복 가능 — 높음

- 근거: AttemptChord는 여러 이웃에 RevealCell을 반복 호출한다. RevealCell은 게임 종료 상태를 검사하지 않으며 GameOver에도 중복 호출 방지가 없다.
- 영향: 잘못 꽂은 깃발로 주변 열기를 했을 때 첫 지뢰로 패배한 후에도 다른 칸을 열거나 종료·광고 이벤트를 추가 발생시킬 가능성이 있다.
- 검증: 숫자와 깃발 수는 같지만 깃발 위치는 틀리고, 주변에 여러 미공개 칸·지뢰가 있는 상태에서 숫자를 누른다. 종료 이벤트·광고 횟수와 최종 결과를 확인한다.

### R08. 10SUM 제한 시간 종료 후 드래그 확정 가능 — 중간

- 근거: OnPointerDown만 IsGameOver를 검사한다. OnDrag, OnPointerUp, ProcessSelectedCells와 AddScore에는 종료 검사가 없다. 최고 점수는 EndGame에서 먼저 확정된다.
- 검증: 종료 직전 합 10 영역의 드래그를 시작하고 0초 이후 손을 뗀다. 입력 전달 여부와 점수·결과 패널·최고 기록 간 일치 여부를 확인한다. 결과 패널에 의한 입력 차단까지 실행으로 확인해야 한다.

### R09. 저장 형식과 복구 처리 — 중간

- 근거: JSON 읽기·역직렬화에 일반적인 예외 복구가 없다. 블록도쿠는 보드와 제공 블록을 별도 파일에 순차 저장한다. 블록 종류는 안정된 ID 대신 AllPossibleBlocks 내 인덱스로 저장한다. 2048은 복원 배열 길이를 보드 크기와 검증하지 않는다.
- 영향: 파일 손상·저장 중 종료·블록 목록 순서 변경 시 로드 실패나 잘못된 블록 복원이 가능하다.
- 검증: 빈 파일, 잘못된 JSON, 부분 필드, 잘못된 배열 길이, 보드 파일만 존재, 블록 정의 순서가 바뀐 업데이트. 원본 사용자 저장본은 보존한 별도 테스트 환경을 사용한다.

## 씬·프리팹 연결 확인

씬의 오래된 UnityEvent 문자열만으로 버튼 불량을 판단하면 안 된다. 실제 대상 fileID와 Awake/Start의 AddListener를 함께 대조했다.

- 2048의 재시작·타이틀 버튼은 직렬화된 대상이 0이지만 UIManager2048.Start에서 다시 연결한다. 현재 확인한 재시작 버튼은 결과 패널의 RetryBtn이다. 따라서 진행 중 재시작 오류라고 단정할 근거는 부족하다.
- 블록도쿠의 설정·재시작·타이틀 버튼도 UIManager_2D.Awake에서 연결한다. 결과 타이틀 버튼에는 존재하지 않는 BackToTitle 이벤트가 남아 있지만 실행 시 별도 리스너가 추가된다.
- 블록도쿠 결과 RetryBtn은 ResetPanelYes에 연결된다. 리셋 확인 패널의 YesBtn은 코드에서 연결된다. 확인 패널의 YesBtn이 동일 메서드를 중복 호출한다고 볼 근거는 없다.
- 지뢰찾기의 EasyBtn/NormalBtn/HardBtn에는 대상 0인 예전 이벤트가 남아 있지만 난이도 선택 리스너를 Awake에서 추가한다. 이름과 오래된 메서드 문자열만 보고 결과 버튼 불량으로 분류하지 않는다.
- 2048 SettingBtn은 씬에서 비활성화되어 있다. 공통 설정 코드가 있다는 사실과 각 게임에서 설정 화면에 접근할 수 있다는 사실을 구분해야 한다.

## 광고·공통 동작

- 전면 광고 횟수는 앱 실행 중 메모리에 유지된다. 게임마다 별도 카운트이며 앱 재실행 시 초기화된다. 광고를 실제 표시할 때 카운트를 0으로 만든다.
- 일부 중도 이탈·재시작은 종료 이벤트에 포함된다. 시스템 뒤로 가기는 UI_Functions에서 바로 Title을 로드해 게임별 GoToTitle 경로를 우회한다. 지뢰찾기·10SUM에서 이탈 경로별 광고 카운트가 달라지는지 확인한다.
- AdManager.LoadInterstitialAd에는 로딩 중 중복 요청 방지 상태가 없다. 초기 로딩·재시도 중 종료 이벤트가 겹치는 상황을 확인해야 한다.
- 광고 완료 콜백은 단일 필드로 보관한다. 광고 표시 직전 반복 버튼 입력이 허용되는지, 중복 씬 이동·광고 요청이 발생하는지 확인한다.
- 자동 플레이를 StopTest로 중단하면 광고를 다시 켜지만, 목표 횟수 달성 후 정상 완료 경로에는 같은 복원 호출이 없다.
- 백그라운드 전환 전용 저장·타이머 처리(OnApplicationPause/OnApplicationQuit)는 사용자 스크립트에서 발견하지 못했다. 실제 OS 정지·복귀 시 타이머 동작과 저장 유지는 실기기에서 확인해야 한다.

## 테스트 자산과 한계

BlockdokuAutoTester는 합격/실패 단언이 없는 자동 플레이·밸런스 분석 도구다. 평균 점수와 종료 시 남은 블록 빈도를 CSV로 내보낸다. 같은 난수 시드를 지정하는 기능은 보이지 않는다. useSmartAI 필드는 선언되어 있으나 현재 분기에서 사용되지 않는다.

자동 플레이는 실제 드래그 입력을 통하지 않고 BlockPlaced를 직접 호출한다. 따라서 터치 좌표, 손가락 가림, 멀티터치, UI 차단, 드래그 취소 문제를 검증하지 못한다. 자체 점수 계산 오류가 있다면 평균 점수 통계도 영향을 받는다. 로직 결함 검증 후 밸런스 지표를 해석해야 한다.

BlockdokuBoard에는 UI와 분리된 배치·제거·대칭 판정이 있지만 현재 GridManager_2D는 별도의 판정 코드를 사용한다. 이 클래스만 테스트해도 실제 플레이 로직이 검증되는 것은 아니다.

## 다음 검토·테스트 순서

1. 키보드 없는 기기의 기본 조작과 게임별 진입·종료를 확인한다.
2. R01~R04의 점수·보드·저장 일관성을 재현하고 증거를 남긴다.
3. 타이머 경계, 연속 입력, 잘못된 깃발, 드래그 중 이탈을 확인한다.
4. 광고 준비·미준비·표시 실패 및 앱 백그라운드 복귀를 확인한다.
5. 추가 기획을 반영해 기대 동작을 확정한 뒤 정식 테스트 케이스와 회귀 테스트 범위를 작성한다.

현재 문서는 코드 검토 기록이다. 실행하지 않은 사례를 테스트 통과·실패나 출시 버전의 확정 결함으로 기록하지 않는다.
